## 2. 显存、内存、存储分别装什么

### 2.1 三种常被混淆的对象

| 对象 | 缓存 / 卸载的内容 | 主要目的与代价 |
|---|---|---|
| **MoE 专家权重** | 模型中各专家的参数，按路由需求读取 | 让总权重大于显存的模型运行；未命中可能触发读盘、PCIe 搬运或 CPU 计算 |
| **KV Cache** | 特定请求前缀产生的注意力 K/V 状态 | 节省重复计算或承载长上下文；需要正确的前缀、位置及版本匹配 |
| **OS swap / 页缓存** | 操作系统管理的内存页 / 文件页 | 不是理解专家路由的调度器；隐式换页可能带来难预测的阻塞 |

[生产部署的 KV 分级](大模型生产级部署与选卡估算.md)和 [swap](../05_技术基础/swap内存处理技术.md)不能替代专家权重卸载方案。`mmap` 文件大小、进程虚拟地址、实际 RAM 驻留和锁页内存也不是同一数字；监控时分开记录，避免重复计入页缓存。

### 2.2 总权重容量不等于 GPU 驻留容量

全 GPU 驻留时，MoE **全部专家权重**都要计入显存，不能只按激活参数估算。但采用专家卸载时，可以只让热点专家在 GPU / RAM 中，其余从 NVMe 按需加载；完整权重仍须存放在可访问的存储中。

GPU 峰值预算至少包括：

```text
非卸载权重 + GPU 专家缓存 + KV Cache
+ 激活 / 工作区 + CUDA Graph / 通信缓冲 + 权重 staging 缓冲
+ 测量后确定的安全余量
```

不能把 GPU / RAM / NVMe 的容量简单相加，当成等速的“大显存”。RAM 还要容纳系统、服务、页缓存和其他应用；pinned RAM 不能像普通可换页内存那样交给 swap 回收。

### 2.3 搬权重到 GPU，还是在 CPU 算

专家未驻留 GPU 时至少有两条路径：

```text
路径 A：RAM / NVMe 中的专家权重 -> GPU staging -> GPU 执行专家
路径 B：激活 -> CPU 执行已有专家权重 -> 输出激活回 GPU
```

[Fiddler 论文](https://arxiv.org/html/2402.07033v3)的 §2.2、§3.1-3.2 分析了这两种策略：小输入时搬权重的代价可能高于 CPU 计算；长 prefill / 较大输入又可能适合把权重搬到 GPU 后批量执行。它证明专家不必全在 GPU，**不意味着 CPU 路径或任意卸载引擎都更快**。

## 3. EAR：量化前后的分布重叠

### 3.1 本笔记采用的定义

在**同一 token 前缀** $h$ 和**同一词表 / token ID 对应关系**上，令：

- $p(x\mid h)$：参考模型的下一 token 概率分布。
- $q(x\mid h)$：候选量化模型的下一 token 概率分布。

两者均归一化，并明确是在原始 softmax 之后，还是在 temperature、top-p、top-k、惩罚与其他 logits 处理之后比较。不同处理设置的数值不能直接混用。

单个前缀的重叠为：

$$
A(h)=\sum_x\min\bigl(p(x\mid h),q(x\mid h)\bigr)
    =1-\frac12\sum_x\left|p(x\mid h)-q(x\mid h)\right|
$$

因此 $A(h)$ 在 0 到 1 之间，等于 **1 减总变差距离（TV）**。对声明好的评估前缀集合取平均，本笔记称为**全词表 EAR**：

$$
\mathrm{EAR}=\frac{1}{N}\sum_{i=1}^{N} A(h_i)
$$

这是可复核的分布诊断定义。原帖关联的 [SLQ 论文 v1](https://arxiv.org/html/2605.02404v1)在式 (3) 中把求和限制到参考分布 $p$ 的 Top-K token，实验指标说明使用 **Top-10 分布**。本文查阅的相关摘录没有明确截断后是否重新归一化，故不能把论文报告值或原帖 EAR 直接当成上述全词表重叠。

若只对保留的 token 求原始概率重叠、未重新归一化，它只是全词表重叠的部分和；若截断后重新归一化，则比较的是截断分布，TV 与接受率的解释也只对应那些分布。报告时须写明 **K、截断集合的选择方式、归一化政策及保留概率质量**，不同口径不能直接比较。

**原帖脚本的前缀来源、处理流程、截断和平均口径仍待核对**。参考模型还必须注明是否量化及运行时版本，避免把运行时差异全归因于量化。只拿 API 返回的少量 top-logprobs，通常无法直接算全词表重叠，不能把缺失概率当成零。

### 3.2 为什么它叫“预期接受率”

在标准的精确投机采样中，草稿从 $q$ 采样，目标分布为 $p$，对草稿 token 使用 $\min(1,p/q)$ 接受规则，并在拒绝时使用正确的残差分布。单步期望接受概率就等于这些实际采样分布的全词表重叠，**不是任意 Top-K 诊断值**。

这一关系见 [Leviathan 等，ICML 2023](https://proceedings.mlr.press/v202/leviathan23a/leviathan23a.pdf) 的定理 3.5、推论 3.6 和附录 A.1。**这里把量化模型当作分布比较对象，不表示部署时已运行投机解码。**

重叠是对称的，但实际多 token 投机过程受前缀、草稿成本、验证长度和调度影响。离线平均 EAR 不等于服务日志中的真实接受率，也不能直接换算成加速倍数；没有额外假设，不能用 `EAR^k` 预测连续接受 k 个 token 的概率。

### 3.3 与其他指标各看什么

| 指标 | 能观察什么 | 不能据此推出什么 |
|---|---|---|
| PPL | 给定语料真实后续 token 的概率 / 语言建模损失 | 不完整描述整个下一 token 分布，也不直接等于 Agent 成功率 |
| KL / KLD | 概率分布的偏离，需声明方向，如 KL(p‖q) | 不是天然“不敏感”；方向、平滑与极小概率会影响数值 |
| JS 散度 | 对称的分布差异诊断 | 不是 EAR 本身；取值范围还取决于对数底 |
| Top-1 一致率 | 两模型最高概率 token 是否一致 | Top-1 不变时，其他概率仍可能变化 |
| 全词表 EAR / TV 重叠 | 全分布共有的概率质量；Top-K 版本须另标口径 | 不判定事实正确、工具调用正确、安全性或长任务成功 |
| 任务评估 | 代码测试、格式合规、工具调用、业务答案等 | 单个短 benchmark 不能覆盖全部长上下文与 Agent 行为 |

**教学反例，非模型实测**：三个 token 的概率从 `(0.6, 0.3, 0.1)` 变成 `(0.6, 0.1, 0.3)`，Top-1 完全一致，但重叠只有 `0.8`。这说明指标看的是不同维度，不证明 EAR 总比 KL 或 PPL 好。

### 3.4 低比特量化的选择边界

- 原作者推荐的 `GSQ IQ2_XS + Fast` 先作为候选，核对权重来源、平均 bits-per-weight、未量化层、校准数据和路由改动；本案例 Fast 属于有损路由档位。
- “2-bit”标号不保证整个模型恰好每参数 2 位；混合精度、scale 等元数据和特殊层都会影响实际大小。
- 不从 MoE 架构推出“比同总参数 Dense 更耐 2-3 bit”；路由器、共享专家和热点专家的敏感度需按模型与任务实测。
- 不把 GSQ、EXL2、AWQ 当作同一格式或同一低位宽方案。AWQ 常见是 4-bit 权重量化，具体支持仍查引擎与模型配置。
- 把量化、Fast、路由偏置和投机解码拆开比较；生产门槛由业务质量与 SLO 决定，**EAR 80% 不是通用上线线**。

## 4. I/O 与显存预算怎样调优

### 4.1 先量路径，再判断瓶颈

对采用“权重搬到 GPU”路径的一个窗口，把搬运字节按**互斥来源**计数：$D_{\rm ram}$ 为从 RAM 缓存命中后传往 GPU 的字节，$D_{\rm disk}$ 为从 NVMe 读出后再传往 GPU 的字节，均按每个输出 token 取平均。读盘数据经过 RAM staging 时不要再计入 $D_{\rm ram}$。若两类数据的表示一致，且读盘权重也经过同一条主机到 GPU 链路，粗略传输时间下界为：

$$
t_{\rm PCIe}\gtrsim\frac{D_{\rm ram}+D_{\rm disk}}{B_{\rm H2D,eff}},
\qquad
t_{\rm disk}\gtrsim\frac{D_{\rm disk}}{B_{\rm disk,eff}}
$$

`B_eff` 是匹配块大小、并发与拓扑的**有效带宽**，不是规格峰值。总读盘量还可能包含无效预取等未传往 GPU 的数据，应另行记录，不能只靠 $D_{\rm disk}$ 代表全部磁盘压力。链路可流水重叠时不能简单相加；分层依赖、排队和小块延迟又可能让实际时间高于带宽下界。这是诊断粗模，不是可靠的 TPS 预测器；CPU 计算或直接 I/O 路径需另建模型。

RAM 增加后若读盘减少、但 H2D 搬运不减，PCIe 瓶颈可能仍在；也可能是新增缓存没有覆盖热点，或瓶颈已经移到计算 / 注意力。**只看到“30→42GB，TPS 不变”，不足以证明内存容量无用。**

### 4.2 按测量结果选工程动作

| 动作 | 观察量与控制变量 | 何时可能失败 |
|---|---|---|
| 双盘分块并行读取 | 同一文件分片、块大小、队列深度；记录单盘 / 双盘读量、p95/p99 延迟、温度 | 两盘共享受限上行链路、分片不均、热降速，或根本不是读盘瓶颈 |
| pinned staging 与异步预取 | H2D 时间、读盘与计算重叠率、staging 峰值、缓存命中 | 锁页过多、预取不准、缓冲挤占 KV / 专家缓存 |
| Prompt 多线程分块读取 | 明确读取的是权重、prompt 文件还是其他数据；分别测 prefill TPS 和 TTFT | 线程争用、随机 I/O 放大，或只提高读盘而不改善首 token 延迟 |
| PCIe / NUMA 拓扑核对 | GPU 协商速率与宽度、NVMe 连接、CPU 根复合体 / 芯片组上行、内存位置 | 标称 x16 实际降宽；GPU 与两盘共享带宽；跨 NUMA 搬运 |
| 句柄 / 缓冲生命周期修复 | 长时间重复请求的句柄数、RSS、pinned RAM、VRAM、失败率 | 单次速度正常，但句柄持续增长或回收后异步任务仍引用旧缓冲 |
| 显存余量扫描 | 最大上下文、峰值并发、prefill / verify 工作区、graph 池和 staging 峰值 | 只测短 prompt，低估峰值或碎片；过多专家驻留挤占 KV |

盘吞吐优先不等于忽略尾延迟。解码存在依赖链，一个必需专家的慢读就可能阻塞下一层；预取只隐藏**来得及且预测正确**的 I/O。

### 4.3 预留 1-2GB 只是试验起点

5090 原帖的“留 2GB”不能推广到所有上下文、并发与引擎。作者提到同一张卡还负责桌面显示；余量应来自峰值测量及超长请求 / 故障压测，KV、草稿模型和 staging 都要算入。

显存不足可能直接 **OOM**，也可能在支持的统一内存、驱动或引擎机制下迁移 / 回退，**不是一定自动溢出到 RAM**。发生迁移时性能可能显著下降；没有日志证据不能把所有突然变慢都叫“显存溢出”。

## 5. 缓存调度与路由偏置不是一回事

### 5.1 先尝试不改模型选择的调度

热点专家驻留、LRU、预取、双盘分片和按请求重排缓存，目标是更快取到**原路由已经选中的专家**，不主动改变专家选择。其实现仍需检查权重、索引、并发与数值正确性，不能只凭“缓存优化”四个字保证输出不变。

Xolotl 的设计说明还描述了按对话统计调整 RAM 驻留的方案；这是与下面路由偏置应分别评估的功能。

### 5.2 Cache-aware / Locality-aware Router

为了优先用已在 GPU 的专家，可以调整路由选择分数。以下只是概念示意，不是项目实现或推荐参数：

```text
选择分数 = 原始分数 + GPU 驻留奖励 - 读盘惩罚
按调整后的分数选专家
```

即使仅修改选择分数、保留原始混合权重，**选中的专家集合也可能变化，模型函数与输出分布就可能变化**。“所有专家仍可到达”不等于“每个 token 选择不变”，也不等于无损。

以偏置关闭为基线，记录各层专家选择变化率、命中率、磁盘字节 / token、EAR 和业务质量。缓存冷热与先前请求可能影响选择，复现实验还要固定或记录这些状态；请求交错、换语言和长 Agent 链都应回归。

企业方案中把它列为**有质量预算的实验性优化**，不要和透明卸载打包默认开启。质量、稳定性或可复现性不达预设标准就撤回；“很小的偏置”并不能提前保证“很小的损失”。

## 6. 投机解码与 MTP 的收益条件

### 6.1 为什么带宽受限仍可能受益

草稿先提出若干 token，目标模型验证后接受其中有效部分。一次目标验证可能复用权重读取并处理多列，所以**中低 QPS 的权重带宽受限场景本来就可能适合投机解码**，这也是 [vLLM v0.29.0 文档](https://docs.vllm.ai/en/v0.29.0/features/speculative_decoding)描述的用途。

但在专家卸载中，多个草稿位置还可能触发更多不同专家，扩大取权重集合。是否节省每个有效 token 的搬运，必须看真实接受长度与验证 I/O，不能只看 GPU 利用率。

### 6.2 可能负收益的情形

| 条件 | 可能的额外成本 |
|---|---|
| 草稿与目标匹配差 / 接受率低 | 草稿计算、验证与拒绝处理没有换来足够有效 token |
| 草稿挤占显存 | KV 或专家缓存变小，反而增加 CPU / NVMe 换入 |
| 验证触发更多未命中专家 | 额外读盘、PCIe 搬运和 staging 等待抵消批量验证收益 |
| 高并发已经充分批处理 / 计算受限 | 草稿与验证竞争资源，单用户延迟和总吞吐不一定同时改善 |
| 草稿长度过长 | 后部接受少，验证工作区和无效计算增加 |
| 长 prompt / 长上下文 | 草稿 prefill、KV 与目标验证的成本改变，短文本结果不可直接外推 |

这些是需要测试的失败条件，不表示高 QPS 或带宽饱和下必然变慢；新方法、动态长度与调度可能改善结果。

### 6.3 MTP、独立草稿与正确性分开核对

MTP（Multi-Token Prediction）可用模型原生的多 token 预测头提出候选，不必等价于另放一个完整 draft model。原生预测头存在，不表示任意引擎版本都支持，也不自动保证速度或采样无损。

正确的精确投机采样可以保持**目标模型的分布**；若目标本身是量化或带路由偏置的模型，保持的是这个目标，而不是未量化参考模型。正确算法也不保证随机采样时每次生成的字符串完全一致；vLLM 文档另说明了浮点与 batch 数值差异。

Fast、跳过验证、近似接受规则或路由改变的正确性要分别审查，不能借“投机解码无损”的名称背书。

## 7. 对照实验与学习验收

### 7.1 先固定一份实验清单

| 记录项 | 最低内容 |
|---|---|
| 模型 / 权重 | 模型 ID 与 revision、量化来源 / 文件 hash、平均位宽、未量化层、校准集与评估集隔离 |
| 软件 | 引擎 commit、驱动 / CUDA、内核、OS、实际配置；Fast、路由与投机参数逐项记录 |
| 硬件 / 拓扑 | GPU、可用 RAM / 锁页预算、双盘型号、文件分片、PCIe 链路与 CPU / NUMA |
| 请求 | 原始 prompt、token 数、输出长度、采样参数、并发 / 到达方式、预热与重复次数 |
| 缓存状态 | GPU / RAM 专家命中，NVMe 读量、OS 页缓存条件、会话缓存与预取状态；声明冷 / 热的定义 |
| 性能 | TTFT、ITL/TPOT 的分位数、prefill TPS、decode TPS、端到端耗时、总吞吐、错误率 |
| 资源 | 峰值 VRAM / RSS / pinned RAM、磁盘尾延迟、H2D 搬运量与时间、句柄数长期变化 |
| 质量 | 同前缀 EAR / KL / Top-1、任务成功率与失败样本；参考是否量化、是否更改路由；EAR 的全词表 / Top-K、归一化与保留质量 |

**TPS 必须有分母**：生成 token 数 / 纯 decode 时间，与生成 token 数 / 含 prefill 的端到端时间，不是同一指标。总吞吐还包含所有请求，不能当成单用户速度。

### 7.2 一次只改变一个因素

1. 建立兼容且未加实验性路由偏置的基线；保存完整配置和质量参考。机器装不下高精度参考时，用同 revision 的外部可访问环境评估，不能把另一模型或有限 API logprobs 冒充全分布参考。
2. 同负载比较量化候选；保持采样和其他加速设置一致，EAR 与任务质量一起看。
3. 固定量化，比较 GPU / RAM 缓存预算与单盘 / 双盘；检查命中率、搬运与尾延迟。
4. 固定缓存，分别测试 Fast 和路由偏置；明确改变的是数值路径、专家选择还是纯调度。
5. 固定目标配置，对照投机关闭 / 开启及不同草稿长度；记录草稿接受长度和单位有效 token 的总成本。
6. 将候选放到短 / 长 prompt、冷 / 热缓存、低 / 目标 / 过载并发、不同语言和长 Agent 任务回归；再检查组合优化的相互影响。

预先声明质量容忍范围、业务 SLO、OOM / 错误率及资源停止条件；收益不稳定或质量不达标时保留基线。单卡“能聊”不等于企业峰值负载可用，企业架构与服务治理见 [HomeLab 到中小企业部署](HomeLab到中小企业LLM部署架构.md)。

### 7.3 学习验收

- **可提交产物**：一份版本固定的配置清单、逐项对照表、原始日志，以及“瓶颈判断 / 反例 / 撤回条件”说明。
- **判定标准**：能区分三种缓存对象；能算教学示例的重叠；每个性能数字能追到负载与计量口径，质量结论能追到参考与任务集。
- **失败案例**：RAM 加大却不提速时，能提出并测量“命中率没变 / PCIe 未减 / 计算受限”等竞争解释；投机加速短文本却使目标并发 p99 变差时，不宣称总体成功。
- **迁移 / 回归**：换语言、换上下文、冷启动和请求交错后重测；不能只用量化校准集证明泛化。
- **当前状态**：由学习者填写，本文没有完成模型实验，不预填“已掌握 / 已验证”。
