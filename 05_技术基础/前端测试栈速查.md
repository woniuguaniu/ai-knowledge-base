# 前端测试栈速查：Vitest / e2e / spec

> 一句话定位：把前端工程里高频出现却容易混的三个词——**Vitest**（单元测试框架）、**e2e**（端到端测试）、**spec**（测试文件）一次讲清，并补上"测试金字塔在前端到底用什么工具落地"。适合有编程基础、但没系统接触过前端测试的人，以及看 `package.json` 里 `vitest run`、看见 `login.spec.ts` 文件犯嘀咕的人。

## 1. 背景与问题

接手或部署一个前端项目时，你大概率会撞见这几样东西：

- `package.json` 里写着 `"test": "vitest run"`，但不知道 **Vitest** 是干嘛的
- 项目里一堆 `xxx.spec.ts` / `xxx.test.ts` 文件，不知道 **spec** 是什么意思
- CI 流水线（持续集成，见 [CI-CD 与 GitHub Actions](CI-CD与GitHub-Actions.md)）的日志里有一步叫 **e2e**，跑得特别慢

这三个词分属测试体系的不同位置，但前端圈天天混着说，新人很容易一锅粥。**本文只解决"这三个词是什么 + 在前端用什么工具 + 怎么串起来"**，不深入讲 mock 技巧、快照测试、覆盖率门槛配置这些进阶话题。

> ⚠️ 一个最常见的坑先剧透：前端代码里的 `.spec` 文件中的 "spec"，和产品经理口中的"产品 Spec / 需求 Spec"**不是一回事**——详见 [3.1](#31-spec测试文件不是产品规格)。

## 2. 核心结论

先给可复习的短表，看完这张表就能应付日常对话：

| 词 | 全称 | 一句话 | 类比 |
|---|---|---|---|
| **Vitest** | 名字来自前端构建工具 **Vite** + test | 前端的**单元测试框架**，测"单个函数 / 组件"这种小单元 | 相当于前端版的 Python **`pytest`** |
| **e2e** | **e**nd-**to**-**e**nd | **端到端测试**，模拟真实用户从头点到尾，测"整条流程能不能用" | 雇个人当真用户，照着剧本把功能走一遍 |
| **spec** | **spec**ification（规格） | 测试语境里特指**测试文件**，约定写成 `xxx.spec.ts` | 一张"考卷"：规定了被测对象应该考出什么答案 |

把三个词连起来：**`checkout.e2e.spec.ts`** = "下单流程的端到端测试用例文件"。

| 问题 | 结论 |
|---|---|
| 它们是什么 | Vitest = 单测工具；e2e = 测试层级；spec = 测试文件命名 |
| 什么时候用 | 几乎所有正经前端项目都该有单测，关键用户流程加 e2e |
| 最大风险 | 把 `.spec` 测试文件和"产品 Spec 文档"搞混；只写 e2e 不写单测导致又慢又脆 |
| 一句话记忆 | **金字塔底层大量 Vitest 单测，顶层少量 e2e，测试都写在 .spec 文件里** |

## 3. 关键概念逐个拆

### 3.1 spec：测试文件，不是产品规格

**一句话理解**：在测试代码里，`spec` 是 specification（规格）的缩写，前端约定把测试代码写进 **`文件名.spec.扩展名`**（如 `button.spec.ts`）或 `文件名.test.扩展名` 里。测试框架靠这个命名约定自动找到所有测试文件来跑。

**生活类比**：`.spec` 文件像一张**考卷**——它写明"这个函数/组件应该考出什么答案"，框架拿着考卷去考被测代码，对不上就判挂科（测试失败）。

**真实例子**：

```text
src/
├── utils/
│   ├── sum.ts            ← 业务代码（被测对象）
│   └── sum.spec.ts       ← 对应的测试文件（spec = 测试规格）
└── components/
    ├── Button.tsx
    └── Button.spec.tsx   ← Button 组件的测试
```

> ⚠️ **`.spec` vs 产品 Spec——同名不同物，必须分清**

这个知识库里到处出现的 "Spec"（比如 [软件工程产品研发 SOP](软件工程产品研发SOP.md) 的"阶段 2：产品 Spec 与验收标准"）指的是**产品规格说明书 / 需求文档**，是给人看的文档。而前端代码里的 `.spec.ts` 是**测试代码文件**，是给机器跑的。两者英文同源（都来自 specification），但完全两回事：

| "Spec" 出现在哪 | 真正含义 | 形态 | 例子 |
|---|---|---|---|
| 代码文件名 `xxx.spec.ts` | 测试规格（test specification） | 一段会被执行的测试代码 | `login.spec.ts` |
| 需求/产品文档里的 Spec | 产品规格说明书（product specification） | 给人读的文档 | 软件工程 SOP 阶段 2 的产品 Spec |

**判断窍门**：看它在哪。出现在**代码目录、带 `.ts/.js/.tsx` 后缀** → 测试文件；出现在**需求评审、文档、阶段产出** → 产品规格。

### 3.2 单元测试与 Vitest

**一句话理解**：**单元测试（unit test）** = 只测一个最小单元（一个函数、一个组件）在给定输入下输出对不对，不连数据库、不开浏览器，所以**又快又准**。**Vitest** 就是目前前端最流行的单元测试框架之一。

**生活类比**：单元测试像**质检流水线上单独测一颗螺丝**——不管整台机器，只验"这颗螺丝尺寸对不对"。快、便宜、坏了一眼定位。

**真实例子**（注意 `.spec.ts` 文件里怎么写）：

```ts
// sum.ts —— 被测的业务函数
export function addNumbers(a: number, b: number): number {
  return a + b
}
```

```ts
// sum.spec.ts —— 对应的单元测试文件
import { describe, it, expect } from 'vitest'
import { addNumbers } from './sum'

// describe：把相关测试分到一组
describe('addNumbers 加法函数', () => {
  // it / test：一个具体测试用例
  it('两个正数相加结果正确', () => {
    // expect 断言：期望 addNumbers(2,3) 等于 5，不等就判失败
    expect(addNumbers(2, 3)).toBe(5)
  })
})
```

跑测试就一行命令：`npx vitest run`（这正是 [GitHub 项目入门指南](GitHub项目入门/小白入门-GitHub项目部署使用指南.md) 里 `package.json` 那行 `"test": "vitest run"` 在干的事）。

**Vitest vs Jest**（两个最常被拿来比的单测框架，新人常纠结选哪个）：

| 维度 | Vitest | Jest |
|---|---|---|
| 出身 | Vite 生态（2021 年后新起） | Meta/Facebook，老牌标准 |
| 速度 | 快（底层用 Vite/esbuild） | 相对慢 |
| 配置 | 几乎零配置，复用项目的 `vite.config` | 常要额外配 babel / ts-jest |
| API | 基本兼容 Jest（`describe/it/expect` 一样） | 业界事实标准 |
| 适合 | Vite / Vue / 新项目 | 老项目、Create React App、React Native |

> 💡 因为 API 高度兼容，从 Jest 迁到 Vitest 通常改动很小，**不用为选哪个纠结太久**：新项目用 Vite 就顺手上 Vitest，老项目跑着 Jest 没坏就别动。

### 3.3 e2e 端到端测试

**一句话理解**：**端到端测试（end-to-end，e2e）** = 启动一个**真浏览器**，像真实用户一样操作整个应用：打开页面 → 点按钮 → 填表单 → 提交 → 检查结果。它测的是"**整条链路串起来到底能不能用**"，而不是某个函数。

**生活类比**：单元测试是单独测螺丝，e2e 则是**把整车开上路跑一圈**——油门刹车转向一起验，最接近真实驾驶，但跑一趟也最费时。

**真实例子**（用 Playwright 写的登录 e2e 用例）：

```ts
// login.e2e.spec.ts —— 端到端测试：模拟真实用户登录
import { test, expect } from '@playwright/test'

test('用户能用正确账号密码登录并跳转首页', async ({ page }) => {
  await page.goto('https://example.com/login')      // 打开登录页
  await page.fill('#username', 'alice')             // 在用户名框输入
  await page.fill('#password', 'secret123')         // 在密码框输入
  await page.click('button[type=submit]')           // 点击登录按钮
  // 断言：登录后地址栏跳到了 /dashboard
  await expect(page).toHaveURL(/dashboard/)
})
```

**前端两大主流 e2e 工具**：

| 工具 | 特点 | 一句话 |
|---|---|---|
| **Playwright** | 微软出品，多浏览器（Chromium/Firefox/WebKit）、自动等待、并行快 | 目前新项目的主流选择 |
| **Cypress** | 老牌，调试体验好（时间旅行回放），但多 Tab / 多浏览器支持弱 | 仍有大量存量项目在用 |

> 本知识库 [软件工程产品研发 SOP](软件工程产品研发SOP.md) 的案例里，"E2E 用 Playwright 覆盖登录、房间、维修、通知"说的就是这一层。

### 3.4 组件与集成测试

**一句话理解**：在"单测"和"e2e"之间还有一层——**组件测试 / 集成测试**：测一个**组件渲染出来 + 用户交互**对不对，或测**几个模块/API+数据库连起来**对不对，但通常不启动真浏览器（用 jsdom 模拟 DOM）。

**生活类比**：介于"测单颗螺丝"和"整车上路"之间，相当于**把发动机总成单独架起来通电试转**——比单测真实，比上路便宜。

**真实例子**：前端最常用 **Testing Library**（`@testing-library/react` 等）配合 Vitest 来测组件：

```ts
// Button.spec.tsx —— 组件测试：渲染按钮并模拟点击
import { render, screen, fireEvent } from '@testing-library/react'
import { describe, it, expect, vi } from 'vitest'
import { Button } from './Button'

describe('Button 组件', () => {
  it('点击后触发回调', () => {
    const handleClick = vi.fn()                  // vi.fn 造一个"假函数"记录是否被调用
    render(<Button onClick={handleClick}>提交</Button>)
    fireEvent.click(screen.getByText('提交'))    // 模拟点击文字为"提交"的元素
    expect(handleClick).toHaveBeenCalledOnce()   // 断言：回调被调用了一次
  })
})
```

## 4. 实战方法

**前端测试金字塔**——记住"底大顶小"这一个形状，就理解了整个栈怎么配比：

```text
            /\
           /  \      e2e 端到端（Playwright / Cypress）
          /----\       少、慢、贵，但最像真实用户
         /      \
        /--------\    组件 / 集成测试（Testing Library + Vitest）
       /          \     适中
      /------------\
     /              \  单元测试（Vitest / Jest）
    /----------------\   多、快、便宜，覆盖大量函数与分支
```

| 层级 | 测什么 | 前端常用工具 | 跑起来 |
|---|---|---|---|
| 单元测试 | 单个函数 / 工具方法 | **Vitest**、Jest | 毫秒级，可成百上千个 |
| 组件 / 集成 | 组件渲染+交互、模块拼接 | **Testing Library** + Vitest（jsdom） | 秒级 |
| e2e | 整条用户流程（含真浏览器） | **Playwright**、Cypress | 几十秒~分钟级 |

**落地流程**（一个典型 Vite 项目从零加测试）：

```text
1. 装依赖：npm i -D vitest @testing-library/react
   （e2e 另装：npm i -D @playwright/test）
   ↓
2. 写测试：业务代码旁边建 xxx.spec.ts
   ↓
3. 配脚本：package.json 里加
     "test": "vitest run"          // 跑单测/组件测试
     "test:e2e": "playwright test" // 跑端到端
   ↓
4. 本地验证：npm test 看全绿
   ↓
5. 接入 CI：push 代码时 GitHub Actions 自动跑这两条
   （见 CI-CD 与 GitHub Actions 笔记）
   ↓
输出 / 验收证据：CI 日志里 "X passed"，红了不许合并
```

这一步"红了不许合并"，正是 [软件工程产品研发 SOP](软件工程产品研发SOP.md) 里**质量门禁**那一节说的 `unit test` / `e2e test` 门禁。

## 5. 常见误区

| 误区 | 为什么错 | 更好的做法 |
|---|---|---|
| 把 `.spec.ts` 文件当成"产品规格文档" | 同名不同物：`.spec` 是测试代码，产品 Spec 是需求文档 | 看后缀和位置：代码目录里带 `.ts/.tsx` 后缀的就是测试 |
| 只写 e2e，不写单元测试 | e2e 又慢又脆（页面一改就挂），出错还难定位是哪一环 | 按金字塔：海量单测打底，关键流程才上 e2e |
| 为"Vitest 还是 Jest"纠结很久 | 两者 API 高度兼容，迁移成本低 | 新/Vite 项目用 Vitest，老项目维持 Jest，别空耗 |
| 在单元测试里连真数据库、开真浏览器 | 那已经不是单测了，会变得又慢又不稳定 | 单测用 mock / jsdom；要测真链路就明确归到集成或 e2e 层 |
| 以为"测试通过 = 没 bug" | 测试只覆盖你写到的用例，没覆盖的照样出问题 | 测试是"防回归"的安全网，配合覆盖率看盲区，但不等于零缺陷 |
