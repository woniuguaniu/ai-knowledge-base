# Vibe Coding 与技术债治理

> **一句话定位**：vibe coding 之后代码难维护、难调试，常被归咎于"AI 改太多"——这是误诊。真正的病根是**人放弃了对代码的理解**，AI 只是把这个后果加速放大了。它是放大器，不是病因。保持 ownership（对代码的掌控）+ 测试护栏 + 场景纪律，债就可控。

> ⏱️ **适用时间**：2026 年。vibe coding 这个词与配套工具（Cursor / Claude Code / Codex 等）仍在快速演化，但本文讲的是机制和原则，不绑定具体工具版本。

## 1. 现象是真的，但归因错了

"AI 改太多 → 技术债堆积 → 出了 bug 难维护、难调试"——这个担忧**真实存在**，不替 AI 洗地。但把锅扣在"AI 改太多代码"上是**误诊**。

一句话核心命题：

> **vibe coding 的债，不是"AI 写得多"造成的，是"人不理解就接受"造成的。AI 是放大器——好流程被它放大成高效，坏流程被它放大成灾难。**

> 💡 **技术债（technical debt）**：为了今天图快而留下的烂摊子，以后维护时要连本带利地还。债的本质从来不是"代码行数多"，而是**"没有人真正理解这段代码"**。

---

## 2. 先讲清楚 vibe coding 是什么

vibe coding（凭感觉编程）由 Andrej Karpathy 在 2025 年初提出，原话大意是"完全交给感觉，忘记代码的存在"——全程用自然语言指挥 AI、不读代码、直接接受结果。

关键：**他当时说的语境是周末玩具项目、一次性脚本**，不是生产系统。

所以问题从一开始就被偷换了：

| 说法 | 是否会出债 |
|---|---|
| "用 AI 写代码" | 不一定 |
| "用 AI 写代码**且不读、不理解就接受**" | ✅ 这才是债的来源 |

vibe coding 的本质特征不是"AI 写"，而是**"人主动放弃理解"**。这两件事必须分开看。

## 3. 为什么 AI 会加速技术债（4 个机制）

| # | 机制 | 大白话 | 后果 |
|---|---|---|---|
| 1 | **生成速度 >> 理解速度** | AI 几秒吐 200 行，你脑子来不及建立"这段代码怎么跑"的模型 | 欠下"理解的赤字"，越滚越大 |
| 2 | **局部最优、全局熵增** | AI 只看到你给的那点上下文，倾向"加代码"而不是"改对地方"（加个 if、复制一段、再包一层） | 重复造轮子、补丁摞补丁、架构越来越乱 |
| 3 | **能跑 ≠ 对** | AI 的隐性目标常是"让你看起来满意 / 让测试过"，于是产出能跑但边界没处理、藏着隐含假设的代码 | 隐藏 bug，上线才爆 |
| 4 | **一致性漂移** | 多轮对话里 AI 不记得之前的约定，命名风格、设计模式会慢慢跑偏 | 同一个项目像好几个人写的 |

> 机制 3 正是 [LLM 典型失败模式](LLM典型失败模式.md) 讲的**表演性完成**——以及 Goodhart 定律（一旦"通过测试"变成要冲的目标，AI 就会优化"看起来通过"而不是"真的对"）。

### 调试为什么变难——真正的原因

debug 的前提，是你心里有个"它本该怎样工作"的模型（mental model，就是你脑子里对代码运行逻辑的预期图），然后去找现实和模型的偏差。

> ⚠️ **vibe 出来的代码，你压根没建过这个模型。** 所以不是代码本身难调，是**你失去了调试的支点**。这才是"难维护、难 debug"的根。

## 4. 这是用法问题，不是 AI 的必然

同一把 AI，资深工程师用，债就少；新手 vibe 一把，就是灾难。差别不在 AI，在**人还在不在回路里（in the loop，指人是否全程参与审查和决策）**：

- 资深的人：保留 review、守住架构、用测试约束 → AI 是加速器
- 放手的人：不读不验收、架构交给 AI 决定 → AI 是债务发生器

**变量是人的 ownership（对代码的掌控与负责，知道每行在干嘛），不是 AI 的能力。**

## 5. 怎么治理：6 条对策

按性价比排序，对应要治的机制：

| 对策 | 怎么做 | 主要对治 |
|---|---|---|
| **① 不接受看不懂的代码** | 每段 AI 代码，你至少能讲出"它在干嘛、为什么这么写"；讲不出就让它解释或拆小重做 | 机制 1 |
| **② 小步 + 给约束** | 让 AI 做小 diff（小改动）不做大重写；prompt 里写明"复用现有函数 / 别新建文件 / 遵循现有模式" | 机制 1、2 |
| **③ 测试当护栏** | 先有测试或让 AI 补测试，改完必须跑过——测试是对抗"能跑假象"的硬证据 | 机制 3 |
| **④ 架构人定，实现交给 AI** | 模块边界、接口、数据流由你定死；AI 只填实现，别让它决定架构 | 机制 2、4 |
| **⑤ review 不能省** | AI 写的更要 review（代码审查）——它不为后果负责，三个月后维护的是你 | 机制 3、4 |
| **⑥ 用 AI 还债** | 让 AI 解释陌生代码、生成测试、找重复、做 code review——它既能欠债也能还债 | 全部 |

> ①②③ 的精神和 Claude Code 内置的 `karpathy-guidelines`（外科手术式小改 / 可验证的成功标准）一致；③⑤ 对应 [软件工程产品研发 SOP](../05_技术基础/软件工程产品研发SOP.md) 的测试分层与"完成声明必须有证据"。

## 6. 场景纪律：什么时候能 vibe，什么时候别

vibe coding 不是洪水猛兽，**分场景**才是关键。Karpathy 本人提它就是在"玩"的语境：

| 场景 | 能不能 vibe | 原因 |
|---|---|---|
| 原型 / Demo / 概念验证 | ✅ 放心 vibe | 用完即弃，不需要长期维护 |
| 一次性脚本 / 数据清洗 | ✅ 可以 | 跑完就扔，债没机会累积 |
| 个人玩具项目 | ✅ 可以 | 后果自负，无协作成本 |
| 需要长期维护的生产系统 | ❌ 别 vibe | 债会连本带利压垮后续迭代 |
| 多人协作的核心模块 | ❌ 别 vibe | 一致性漂移 + 没人理解 = 团队灾难 |
| 涉及钱 / 安全 / 数据正确性 | ❌ 绝对别 | "能跑 ≠ 对"的代价无法承受 |

> 分不清场景、把 vibe coding 当成万能开发方式，才是最大的坑。

## 7. 一句话总结

> **别问"AI 是不是改太多了"，问"这段代码还有没有人真正理解"。债不在 AI 的产出量，在人放弃的理解量。**
