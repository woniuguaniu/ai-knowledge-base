## 1. 为什么薪资高：能力分层与市场供需

核心洞察：**薪资溢价正在沿着"能力分层"重新分配**。同样是做 AI，做"低端"和做"高端"的市场价正在拉开。

| 能力层级 | 典型工作 | 市场状态 |
|---|---|---|
| **低端（会用 AI）** | 大模型 API 调用、RAG 知识库问答、简单问答机器人 | 溢价正在消失——门槛被拉平，人人都能上手 |
| **高端（造 Agent 系统）** | 多 Agent 协同、Agent 工作流、记忆体系、工具调用编排、规划推理、反思迭代、Agent 安全、调度引擎、分布式 Agent、长周期任务自治 | 溢价极高——能稳定交付的人稀缺 |

**为什么分界线在这里？** 因为企业真正付费的不是"会调 API"，而是能把 Agent 做成一套 **自主运行、可扩展、可管控、可运维** 的系统。这四个词，每一个都是一整套工程：

| 企业要的特性 | 翻译成工程语言 |
|---|---|
| 自主运行 | 不靠人盯着也能连续跑（ReAct 循环 + 错误恢复 + 兜底） |
| 可扩展 | 加业务 / 加工具不用推倒重写（清晰的模块边界 + 编排层） |
| 可管控 | 出事能拦得住、能回滚（权限闸门 + 人工确认 HITL + 审计日志） |
| 可运维 | 线上能调试、能持续优化（Trace 链路 + Eval 评测 + 成本监控） |

> ⚠️ **清醒提醒**：标题里的"薪资高"本身是培训课的营销话术，"低端溢价完全消失 / 高端溢价极高"也说得过于绝对（缺岗位、行业、交付责任的边界）。这个角色**真实存在**，但招聘市场上更常见的 title 是 **AI Engineer / Applied AI Engineer / LLM Systems Engineer**——"Agent 架构师"这个词本身在招聘网站几乎搜不到。对这个"造词"的完整辨析见 [Agent发展轨迹四阶段 § 10.3](Agent发展轨迹四阶段.md#103-这个定义的可商榷之处)。

## 2. Agent 架构师能力地图（8 大能力域）

把上表那 10 项零散的高端需求，重新归并成 **8 个能力域**。每域给"核心知识点 / 典型工程组件 / 企业落地要解决的真实问题"。这份归并是 **Claude 与 Codex 两个模型独立分析后高度一致**的结果（两边都收敛到这 8 个域，只是命名略有出入）。

| # | 能力域 | 核心知识点 | 典型工程组件 | 企业落地要解决的真实问题 |
|---|---|---|---|---|
| 1 | **工程化架构** | 封装 / 配置 / 编排 / 服务化、模块边界、环境隔离 | API 封装层、配置中心、服务化框架 | 让 Agent 从一次性 Demo 变成能部署、能复用的系统 |
| 2 | **规划与任务分解** | 意图识别、路由、Planner、子任务拆解、依赖管理 | Router、Planner、任务图（DAG） | 复杂任务没法一次答完，要会拆步骤、定先后、管依赖 |
| 3 | **工具调用与行动编排** | Function Calling、MCP、工具选择、权限、失败重试 | Function Calling、MCP Server、沙盒 | 让 Agent 安全可靠地操作外部系统（查 / 改 / 执行代码） |
| 4 | **记忆与上下文管理** | 长短期记忆、Session、Workspace、Checkpoint、Resume、上下文压缩 | 向量库、状态存储、断点续跑机制 | 支撑跨轮次 / 跨时间 / 跨文件的长程任务而不丢状态 |
| 5 | **多 Agent 协同** | 角色分工、任务派发、冲突处理、结果汇聚、调度 | SubAgent、消息总线、调度引擎、共享真相源（Single Source of Truth） | 单 Agent 能力有边界，复杂流程要并行 / 分工 / 汇总 |
| 6 | **反思与质量控制** | Self-check、结果校验、Eval、回滚、人工确认（HITL，Human-in-the-Loop，人在回路审批） | Eval 数据集、LLM-as-Judge（用大模型当裁判）、回滚机制 | 压住幻觉 / 错误执行 / 不可控输出，"变好了"得有数 |
| 7 | **可观测与运维** | Trace（调用链路追踪）、日志、成本监控、延迟、失败率、版本管理 | Tracing、Metrics 指标、成本看板 | 线上能调试、能审计、能优化、能持续上线 |
| 8 | **安全与治理** | 权限边界、数据隔离、Prompt 注入防护、合规、审批流 | 权限闸门、沙箱、注入检测、DLP（Data Loss Prevention，数据防泄漏） | 防 Agent 越权 / 泄密 / 误操作 |

### 框架之外：5 个 PPT 没讲、但企业落地真正卡脖子的能力

这是 **Codex 独立分析时补充**的——上面两页课程偏"技术能力清单"，但真到企业落地，下面这五项往往才是项目成败的关键：

| 漏项 | 为什么关键 |
|---|---|
| **产品与业务建模** | Agent 架构不是堆能力，**先**得定义业务目标、自动化边界、人工介入点、ROI（投入产出比），再谈技术 |
| **数据治理** | RAG 不只是"检索"，还涉及数据质量、权限、更新、溯源、敏感信息处理 |
| **人机协同设计** | 企业 Agent 很少完全自治，关键是想清楚**哪些节点自动化、哪些要人确认 / 审批 / 接管** |
| **测试体系** | 除了 Eval，还需要单元测试、集成测试、回归集、仿真环境、故障注入 |
| **组织与流程集成** | Agent 要接进 CRM / ERP / 工单 / 权限 / 审计 / SOP，而不是孤立运行 |

> 💡 这五项里，"反馈 / Eval"这一块在课程的[学习路线阶段⑥](#3-学习路线6-个能力边界阶段)其实补上了——比同源的"职业定义页"（[§ 10 评析](Agent发展轨迹四阶段.md#10-职业视角什么是-agent-架构师)曾批它漏掉反馈层）要强。

## 4. 这套框架值几分：Claude × Codex 双模型评分

按本知识库"先评分再吸收，不照单全收"的规矩，对素材打分（满分 10）。两个模型分别独立评：

| 评估者 | 评分 | 一句话理由 |
|---|---|---|
| Claude（对同源的"职业定义页"，见 [§ 10.5](Agent发展轨迹四阶段.md#105-agent-架构师概念的综合评分)） | 6.5 / 10 | 看个轮廓不错，但造词 + 漏反馈层 |
| Claude（对本文这两页：薪资 + 学习主线） | 7 / 10 | "按能力边界递进"是真亮点，但薪资页营销话术偏重 |
| Codex（独立分析） | 7 / 10 | 主线递进方向正确，但偏能力清单，漏业务 / 数据 / 组织维度 |

**说对了什么**（两模型共识）：

- ✅ "**按能力边界递进，不按组件清单堆叠**"——这是真正好的框架设计思路
- ✅ 6 阶段路径（骨架 → 回路 → 工具 → 复杂 → 长程 → 落地）覆盖了主干，顺序合理
- ✅ "会用 AI vs 造 Agent 系统"的鸿沟判断方向正确（工程难度差约 2 个数量级，见 [§ 10.2](Agent发展轨迹四阶段.md#102-这个定义说对了什么)）

**漏了 / 可商榷**（Claude + Codex 合并）：

- ⚠️ **营销话术**：标题"薪资高"、"溢价消失 / 极高"过于绝对、"长周期任务自治"容易被包装成"全自动"幻想、"会用 AI vs 架构师"的二分法偏销售口吻
- ⚠️ **漏产品与业务建模**（Codex）：该先定业务目标 / 自动化边界 / ROI，再堆能力
- ⚠️ **漏数据治理**（Codex）：数据质量 / 权限 / 溯源 / 敏感信息，不只是"检索"
- ⚠️ **漏人机协同设计**（Codex）：哪些节点要人确认 / 审批 / 接管
- ⚠️ **漏测试体系**（Codex）：单元 / 集成 / 回归 / 仿真 / 故障注入，不只 Eval
- ⚠️ **漏组织与流程集成**（Codex）：接进 CRM / ERP / 工单 / 审计 / SOP

## 5. 能力跃迁的本质（一句话）

Claude 与 Codex 两个模型**不约而同**指向同一句话：

> 从"会用 AI"到"Agent 架构师"，本质是从 **调用模型生成一个答案**，跃迁到 **设计一套可控、可观测、可恢复、可扩展、并能嵌入真实业务流程的自治系统**。

换句话说：前者交付"**一次正确的输出**"，后者交付"**一个能连续跑不挂、出事能回滚、线上能优化**的系统"。后者的工程难度，比前者高约 **2 个数量级**。
